<span id="summary" />

*Since: forever*

Управляет частями документа, хранящими состояние.

Допустим, у вас есть некоторые вычисления в документе, и вы хотите запомнить результат последнего вычисления, чтобы использовать его в следующем. Вы можете попробовать что-то похожее на код ниже и ожидать, что он выведет 10, 13, 26 и 21. Однако в Typst это **не работает**. Если вы протестируете этот код, вы увидите, что Typst выдаст следующее сообщение об ошибке: _Переменные вне функции доступны только для чтения и не могут быть изменены._

```typst
// This doesn't work!
#let star = 0
#let compute(expr) = {
  star = eval(
    expr.replace("⭐", str(star))
  )
  [New value is #star.]
}

#compute("10") \
#compute("⭐ + 3") \
#compute("⭐ * 2") \
#compute("⭐ - 5")
```

## Состояние и разметка документа [#state-and-markup]

Почему так происходит? Потому что в целом такого рода вычисления с побочными эффектами проблематичны в разметке документа, и Typst честно об этом предупреждает. Чтобы результаты имели смысл, вычисление должно выполняться в том же порядке, в котором результаты будут размещены в документе. В нашем простом примере это так, но в общем случае это может быть не так.

Давайте рассмотрим немного другой, но похожий вид состояния: нумерацию заголовков. Мы хотим увеличивать счётчик заголовков при каждом заголовке. Достаточно просто, верно? Просто добавьте единицу. Что ж, всё не так просто. Рассмотрим следующий пример:

<TypstRender
  code={`
  #set heading(numbering: "1.")
  #let template(body) = [
    = Outline
  ...
  #body
  ]

  #show: template
  = Introduction
  ...
`}
  image="/typst_docs_assets/images/K_KwPhXuYGNEV7A2CuvV_Q.png"
  alt=""
  editable={true}
/>

Здесь Typst сначала обрабатывает тело документа после правила show, видит заголовок `Introduction`, затем передаёт полученное содержимое в функцию `template` и только потом видит `Outline`. Простой подсчёт пронумеровал бы `Introduction` как `1`, а `Outline` как `2`.

## Управление состоянием в Typst [#state-in-typst]

Так что же мы делаем вместо этого? Мы используем систему управления состоянием Typst. Вызов функции `state` со строковым ключом-идентификатором и необязательным начальным значением даёт вам значение состояния, которое предоставляет несколько функций. Две наиболее важные из них — `get` и `update`:

- Функция [`get`](#definitions-get) извлекает текущее значение состояния. Поскольку значение может меняться по ходу документа, это _контекстная_ функция, которую можно использовать только тогда, когда доступен [контекст](/docs/typst/reference/context).
- Функция [`update`](#definitions-update) изменяет состояние. Вы можете передать ей любое значение. Если передано значение, не являющееся функцией, она устанавливает состояние в это значение. Если передана функция, эта функция получает предыдущее состояние и должна вернуть новое состояние.

Наш первоначальный пример теперь будет выглядеть так:

<TypstRender
  code={`
  #let star = state("star", 0)
  #let compute(expr) = {
    star.update(old =>
  eval(expr.replace("⭐", str(old)))
    )
    [New value is #context star.get().]
  }

  #compute("10") \\
  #compute("⭐ + 3") \\
  #compute("⭐ * 2") \\
  #compute("⭐ - 5")
`}
  image="/typst_docs_assets/images/ILRxku4kG3sMvpiLONoWhA.png"
  alt=""
  editable={true}
/>

Состояние, управляемое Typst, всегда обновляется в порядке вёрстки, а не в порядке вычисления. Метод `update` возвращает содержимое, и его эффект проявляется в той позиции, где возвращённое содержимое вставляется в документ.

В результате теперь мы также можем сохранять некоторые вычисления в переменных, но они по-прежнему показывают правильные результаты:

<TypstRender
  code={`
  ...
  #let more = [
    #compute("⭐ * 2") \\
  #compute("⭐ - 5")
  ]

  #compute("10") \\
  #compute("⭐ + 3") \\
  #more
`}
  image="/typst_docs_assets/images/ILRxku4kG3sMvpiLONoWhA.png"
  alt=""
  editable={true}
/>

Этот пример, конечно, немного глуповат, но на практике это часто именно то, что вам нужно! Хороший пример — счётчики заголовков, поэтому [система счётчиков](/docs/typst/reference/introspection/counter) Typst очень похожа на его систему состояний.

## Путешествия во времени [#time-travel]

Используя систему управления состоянием Typst, вы также получаете возможности путешествий во времени! Мы можем узнать, каким будет значение состояния в любой позиции документа из любого другого места. В частности, метод `at` даёт нам значение состояния в любой конкретной позиции, а метод `final` даёт нам значение состояния в конце документа.

<TypstRender
  code={`
  ...

  Value at \`<here>\` is
  #context star.at(<here>)

  #compute("10") \\
  #compute("⭐ + 3") \\
  *Here.* <here> \\
  #compute("⭐ * 2") \\
  #compute("⭐ - 5")
`}
  image="/typst_docs_assets/images/JNIz3N1N6VH1Dhp-T6cK4w.png"
  alt=""
  editable={true}
/>

## Слово предостережения [#caution]

Чтобы вычислить значения всех состояний, Typst вычисляет части вашего кода несколько раз. Однако нет гарантии, что ваши манипуляции с состоянием действительно можно полностью вычислить.

Например, если вы генерируете обновления состояния в зависимости от конечного значения состояния, результаты могут никогда не сойтись. Пример ниже иллюстрирует это. Мы инициализируем наше состояние значением `1`, а затем обновляем его до его собственного конечного значения плюс 1. Значит, оно должно быть `2`, но тогда его конечное значение равно `2`, значит, оно должно быть `3`, и так далее. Этот пример отображает конечное значение, потому что Typst просто сдаётся после нескольких попыток.

<TypstRender
  code={`
  // This is bad!
  #let x = state("key", 1)
  #context x.update(x.final() + 1)
  #context x.get()
`}
  image="/typst_docs_assets/images/QwCkNtt82_6EnW5-GWHZGg.png"
  alt=""
  editable={true}
/>

В целом, вам следует стараться не генерировать обновления состояния из контекстных выражений. Если возможно, попробуйте выразить свои обновления как неконтекстные значения или функции, которые вычисляют новое значение из предыдущего. Иногда этого не избежать, но в таких случаях именно на вас возлагается ответственность за то, чтобы результат сходился.

## Конструктор [#constructor]

Создаёт новое состояние, идентифицируемое ключом.

```typst
state(
  str,
  any,
) -> state
```

### `key` [#constructor-key]

**Тип:** [str](/docs/typst/reference/foundations/str) · **Модификаторы:** Обязательный, Позиционный

Ключ, идентифицирующий это состояние.

Любые [обновления](#definitions-update) состояния будут идентифицироваться строковым ключом. Если вы создадите несколько состояний с одним и тем же `key`, то обновление любого из них повлияет на все.

### `init` [#constructor-init]

**Тип:** `any` · **Модификаторы:** Позиционный · **По умолчанию:** `none`

Начальное значение состояния.

Если вы создадите несколько состояний с одним и тем же `key`, но разными значениями `init`, каждое из них будет использовать своё собственное начальное значение, но разделять обновления. В частности, значение состояния в некоторой позиции документа будет вычислено из начального значения этого состояния и всех предшествующих обновлений для ключа этого состояния.

<TypstRender

  #let banana = state("key", "🍌")
  #let broccoli = state("key", "🥦")

  #banana.update(it => it + "😋")

  #context [
    - #state("key", "🍎").get()

    - #broccoli.get()
  ]
`}

## Функции [#functions]

### `get` [#definitions-get]

*Контекстная* · *Since: 0.11.0*

Извлекает значение состояния в текущей позиции.

Это эквивалентно `state.at(here())`.

```typst
self.get() -> any
```

### `at` [#definitions-at]

*Контекстная* · *Since: forever*

Извлекает значение состояния в уникальном совпадении заданного селектора.

`selector` должен соответствовать ровно одному элементу в документе. Наиболее полезными видами селекторов для этого являются [метки](/docs/typst/reference/foundations/label) и [позиции](/docs/typst/reference/introspection/location).

```typst
self.at(label | selector | location | function) -> any
```

#### `selector` [#definitions-at-selector]

**Тип:** [label](/docs/typst/reference/foundations/label) или [selector](/docs/typst/reference/foundations/selector) или [location](/docs/typst/reference/introspection/location) или [function](/docs/typst/reference/foundations/function) · **Модификаторы:** Обязательный, Позиционный

Место, в котором следует извлечь значение состояния.

### `final` [#definitions-final]

*Контекстная* · *Since: forever*

Извлекает значение состояния в конце документа.

```typst
self.final() -> any
```

### `update` [#definitions-update]

*Since: forever*

Обновляет значение состояния.

Возвращает невидимый фрагмент [содержимого](/docs/typst/reference/foundations/content), который необходимо вставить в документ, чтобы обновление вступило в силу. Это невидимое содержимое сообщает Typst, что указанное обновление должно произойти там, где содержимое вставляется в документ.

Состояние является частью вашего документа и работает как нить, встроенная в содержимое документа. Значение состояния — это результат всех обновлений состояния, произошедших в документе до этой точки.

Вот почему `state.update` возвращает невидимый фрагмент содержимого, который вам нужно вернуть и включить в документ — обновление состояния, которое не «размещено» в документе, не происходит, а «когда» оно происходит, определяется тем, где вы его размещаете. Вот также почему вам нужен [контекст](/docs/typst/reference/context) для чтения состояния: вам нужно использовать текущую позицию документа, чтобы знать, где на «нити» состояния вы находитесь.

Сохранение обновления состояния в переменной (например, `let my-update = state("key").update(c => c * 2)`) само по себе не даст эффекта. Только когда вы вставите переменную `#my-update` куда-нибудь в содержимое документа, обновление вступит в силу — в той позиции, где оно было вставлено. Вы также можете использовать `#my-update` несколько раз в разных позициях. Тогда обновление также вступит в силу несколько раз.

В отличие от [`get`](#definitions-get), [`at`](#definitions-at) и [`final`](#definitions-final), эта функция не требует [контекста](/docs/typst/reference/context). Это потому, что для создания обновления состояния нам не нужно знать, где в документе мы находимся. Эта информация нужна нам только для вычисления значения состояния.

```typst
self.update(function | any) -> content
```

#### `update` [#definitions-update-update]

**Тип:** [function](/docs/typst/reference/foundations/function) или `any` · **Модификаторы:** Обязательный, Позиционный

Значение, до которого нужно обновить, или функция, с помощью которой нужно обновить.

- Если передано значение, не являющееся функцией, устанавливает состояние в это значение.
- Если передана функция, эта функция получает предыдущее значение состояния и должна вернуть новое значение состояния.

При обновлении состояния на основе его предыдущего значения следует предпочитать функциональную форму вместо извлечения предыдущего значения из [контекста](/docs/typst/reference/context). Это позволяет компилятору эффективно вычислять конечное состояние, минимизируя количество требуемых [итераций вёрстки](/docs/typst/reference/context#compiler-iterations).

В следующем примере `fill.update(f => not f)` будет окрашивать нечётные [элементы маркированного списка](/docs/typst/reference/model/list#definitions-item) как ожидается. Однако если заменить его на `context fill.update(not fill.get())`, то вёрстка не сойдётся за 5 попыток, так как каждому обновлению потребуется одна дополнительная итерация для распространения.

  #let fill = state("fill", false)

  #show list.item: it => {
    fill.update(f => not f)
    context {
      set text(fill: fuchsia) if fill.get()
      it
    }
  }

  #lorem(5).split().map(list.item).join()
`}
