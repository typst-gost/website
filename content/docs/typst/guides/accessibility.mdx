Сделать документ доступным означает, что его смогут использовать и понять все. Это касается не только людей с постоянной или временной инвалидностью, но и тех, кто использует другие устройства или имеет иные предпочтения. Чтобы подчеркнуть важность доступности, учтите, что люди могут читать ваш документ в большем числе контекстов, чем вы ожидаете:

- Пользователь может распечатать документ на бумаге
- Пользователь может читать ваш документ на телефоне с включённым в его программе просмотра PDF режимом переформатирования
- Пользователь может попросить компьютер прочитать документ ему вслух
- Пользователь может попросить искусственный интеллект составить для него краткое изложение вашего документа
- Пользователь может преобразовать ваш документ в другой формат файла, например HTML, который для него более доступен

Чтобы учесть всех этих людей и все эти сценарии, следует проектировать документ с расчётом на **универсальный доступ.** Универсальный доступ — это простой, но мощный принцип: вместо того чтобы дорабатывать проект для доступности постфактум, проектируйте его с самого начала так, чтобы он работал для максимально широкого круга людей и ситуаций. Это улучшит опыт для всех читателей!

Typst может помочь вам создавать доступные файлы, которые хорошо читаются программами экранного доступа, хорошо выглядят даже при переформатировании под другой размер экрана и проходят автоматические проверки доступности. Однако для создания доступных файлов вам придётся помнить о некоторых правилах. Это руководство поможет вам узнать, какие проблемы влияют на доступность, как проектировать с расчётом на универсальный доступ и какие инструменты Typst предоставляет для этого. Значительная часть рекомендаций здесь применима ко всем целям экспорта, но руководство сосредоточено на экспорте в PDF. Заметные отличия при экспорте в HTML отмечены отдельно.

## Основы доступности [#basics]

Доступные файлы позволяют программному обеспечению делать с ними больше, чем просто отображать их. Вместо этого ваш компьютер может понимать, что должен представлять каждый фрагмент документа, и использовать эту информацию, чтобы представить документ пользователю.

Эта информация используется различным программным обеспечением для обеспечения доступа. При экспорте PDF из Typst _программа просмотра PDF_ (иногда также называемая программой чтения) отображает страницы документа точно так, как вы их спроектировали в предварительном просмотре Typst. Некоторые люди полагаются на _вспомогательные технологии_ (ВТ), такие как программы экранного доступа, брайлевские дисплеи, экранные лупы и другое, для работы с PDF-файлами. В этом случае семантическая информация в файле используется для адаптации содержимого файла в устный или письменный текст либо в иное визуальное представление. Другие пользователи заставят программу просмотра PDF переформатировать файл, чтобы создать макет, похожий на веб-страницу: содержимое будет подстраиваться под ширину области просмотра и прокручиваться непрерывно. Наконец, некоторые пользователи перепрофилируют PDF в другой формат, например в простой текст для загрузки в большую языковую модель (LLM) или в HTML. Особая форма перепрофилирования — это копирование и вставка, когда пользователи используют буфер обмена, чтобы извлечь содержимое из файла и использовать его в другом приложении.

Поддержка доступности различается в зависимости от программы просмотра и ВТ. Некоторые комбинации работают лучше других. В наших тестах [Adobe Acrobat](https://www.adobe.com/acrobat.html) в паре с [NVDA](https://www.nvaccess.org/download/) на Windows и [VoiceOver](https://support.apple.com/guide/voiceover/welcome/mac) на macOS обеспечивали самую богатую поддержку доступности. В паре с экспортом в HTML браузеры обеспечивают более стабильную базовую доступность по сравнению с программами чтения PDF.

Только экспорт в PDF и HTML создаёт доступные файлы. Ни PNG, ни SVG сами по себе не являются доступными. Оба формата можно использовать в доступной более крупной работе, предоставив [текстовое представление](#textual-representations).

## Сохранение семантики [#maintaining-semantics]

Чтобы добавить в файл корректную семантическую информацию для ВТ и перепрофилирования, Typst должен знать, какую семантическую роль играет каждая часть файла. Например, это означает, что заголовок в скомпилированном PDF не должен быть просто крупным и полужирным текстом. Вместо этого файл должен содержать явную информацию (известную как _тег_) о том, что определённый текст составляет заголовок. Тогда программа экранного доступа объявит его как заголовок и позволит пользователю перемещаться между заголовками.

Если вы используете Typst идиоматически, применяя встроенную разметку и элементы, Typst автоматически добавляет в ваши файлы теги с богатой семантической информацией. Давайте рассмотрим два примера кода:

<TypstRender
  code={`
  // ❌ Don't do this
  #text(
    size: 16pt,
    weight: "bold",
  )[Heading]
`}
  image="/typst_docs_assets/images/MEzKkrZUX0IUb6SEoDt3Gw.png"
  alt=""
  editable={true}
/>

<TypstRender
  code={`
  // ✅ Do this
  #show heading: set text(size: 16pt)
  = Heading
`}
  image="/typst_docs_assets/images/MEzKkrZUX0IUb6SEoDt3Gw.png"
  alt=""
  editable={true}
/>

Оба этих примера выглядят одинаково. Оба содержат текст «Heading» полужирным шрифтом размером 16 пунктов. Однако доступен только второй пример. Используя разметку заголовка, Typst знает, что семантическое значение этого текста — это заголовок, и может передать эту информацию в итоговый PDF. В первом примере он знает лишь, что следует использовать полужирный шрифт и более крупный кегль для обычного в остальном текста, и не может предположить, что вы имели в виду именно заголовок, а не стилистический выбор или какой-то другой элемент, например цитату.

Использование семантики не ограничивается заголовками. Вот ещё несколько примеров элементов, которые следует использовать:

- Используйте подчёркивания / [`emph`](/docs/typst/reference/model/emph) вместо функции [`text`](/docs/typst/reference/text/text), чтобы выделить текст
- Используйте звёздочки / [`strong`](/docs/typst/reference/model/strong) вместо функции text, чтобы придать тексту сильный акцент
- Используйте списки ([`list`](/docs/typst/reference/model/list), [`enum`](/docs/typst/reference/model/enum), [`terms`](/docs/typst/reference/model/terms)) вместо обычного текста с переводами строк при работе с маркированным или нумерованным содержимым
- Используйте [`quote`](/docs/typst/reference/model/quote) для встроенных и блочных цитат
- Используйте встроенные функции [`bibliography`](/docs/typst/reference/model/bibliography) и [`cite`](/docs/typst/reference/model/cite) вместо ручного вывода библиографии
- Используйте метки и [`ref`](/docs/typst/reference/model/ref) или `@references` для ссылок на другие части ваших документов вместо простого набора ссылки вручную
- Используйте [`аргумент caption элемента figure`](/docs/typst/reference/model/figure#definitions-caption) для подписей вместо добавления их в виде текста под вызовом функции

Если вы хотите стилизовать внешний вид элемента по умолчанию, не заменяйте его собственной пользовательской функцией. Вместо этого используйте [правила set](/docs/typst/reference/styling#set-rules), show-set и [правила show](/docs/typst/reference/styling#show-rules), чтобы настроить его внешний вид. Вот пример того, как можно изменить внешний вид сильного акцента в вашем документе:

<TypstRender
  code={`
  // Change how text inside of strong emphasis looks
  #show strong: set text(tracking: 0.2em, fill: blue, weight: "black")

  When setting up your tents, *never forget* to secure the pegs.
`}
  image="/typst_docs_assets/images/_C_9BqFB27kkAm2fb0Dfag.png"
  alt=""
  editable={true}
/>

Правило show-set полностью меняет внешний вид элемента [`strong`](/docs/typst/reference/model/strong) по умолчанию, но его семантическое значение сохраняется. Если вам нужна ещё большая настройка, вы можете предоставить правила show с полностью пользовательским кодом макета, и Typst всё равно сохранит семантическое назначение элемента.

## Порядок чтения [#reading-order]

Чтобы ВТ читали содержимое документа в правильном порядке, а приложения для перепрофилирования работали корректно, доступные файлы должны явно задавать свой порядок чтения. Это связано с тем, что логический порядок чтения может отличаться от порядка макета. Плавающие рисунки — распространённый пример такого различия: рисунок может быть связан с абзацем в центре страницы, но появляться у верхнего или нижнего края. В недоступных файлах программы чтения PDF и ВТ вынуждены предполагать, что порядок макета равен логическому порядку чтения, что часто приводит к путанице у пользователей ВТ. Когда порядок чтения чётко определён, программы экранного доступа читают сноску или плавающий рисунок сразу там, где это имеет смысл.

К счастью, разметка Typst уже подразумевает единый порядок чтения. Можно исходить из того, что документы Typst будут читаться в том порядке, в котором содержимое размещено в разметке. Для большинства документов этого достаточно. Однако при использовании функции [`place`](/docs/typst/reference/layout/place) и [`move`](/docs/typst/reference/layout/move) или [плавающих рисунков](/docs/typst/reference/model/figure#parameters-placement) вы должны уделить особое внимание тому, чтобы разместить вызов функции в подходящем месте логического порядка чтения в разметке, даже если это не влияет на макет. Просто спросите себя, где бы вы хотели, чтобы программа экранного доступа объявила размещаемое вами содержимое.

## Контейнеры макета [#layout-containers]

Typst предоставляет некоторые контейнеры макета, такие как [`grid`](/docs/typst/reference/layout/grid), [`stack`](/docs/typst/reference/layout/stack), [`box`](/docs/typst/reference/layout/box), [`columns`](/docs/typst/reference/layout/columns) и [`block`](/docs/typst/reference/layout/block), для визуального упорядочивания содержимого. Ни один из этих контейнеров не несёт никакого семантического значения. Typst сохранит некоторые из этих контейнеров при переформатировании PDF, а другие контейнеры будут отброшены.

При проектировании с расчётом на универсальный доступ вам нужно учитывать, что пользователи ВТ часто не могут видеть визуальный макет, создаваемый контейнером. Вместо этого ВТ просто прочитают его содержимое, поэтому лучше рассматривать эти контейнеры как прозрачные с точки зрения доступности. Например, содержимое grid будет просто прочитано подряд, в том порядке, в котором вы добавили ячейки в исходном коде. Если созданный вами макет является лишь визуальным и декоративным, это нормально. Если же макет несёт семантическое значение, очевидное для зрячего пользователя, просматривающего файл в обычной программе чтения PDF, то он недоступен. Вместо этого создайте альтернативное представление вашего содержимого, использующее текст, или оберните ваш контейнер в элемент [`figure`](/docs/typst/reference/model/figure), чтобы предоставить альтернативное текстовое описание.

Не используйте контейнер grid для представления табличных данных. Вместо этого используйте [`table`](/docs/typst/reference/model/table). Таблицы доступны пользователям ВТ: их ВТ позволит им перемещаться по таблице в двух измерениях. Таблицы сохраняются при переформатировании и перепрофилировании. При создании таблиц используйте элементы [`table.header`](/docs/typst/reference/model/table#definitions-header) и [`table.footer`](/docs/typst/reference/model/table#definitions-footer), чтобы разметить семантические роли отдельных строк. Документация по таблицам содержит [раздел о доступности](/docs/typst/reference/model/table#accessibility) с дополнительной информацией о том, как сделать ваши таблицы доступными. Имейте в виду, что хотя пользователи ВТ и могут получать доступ к таблицам, это часто для них обременительно: таблицы оптимизированы для визуального восприятия. Чтение содержимого набора ячеек с необходимостью вспоминать их строку и столбец создаёт дополнительную умственную нагрузку. Подумайте о том, чтобы сделать основную суть таблицы доступной в виде текста или подписи в другом месте.

Аналогично, если вы используете такие функции, как [`rotate`](/docs/typst/reference/layout/rotate), [`scale`](/docs/typst/reference/layout/scale) и [`skew`](/docs/typst/reference/layout/skew), позаботьтесь о том, чтобы это преобразование либо не имело семантического значения, либо его значение было доступно пользователям ВТ в другом месте, то есть в [альтернативном тексте](#textual-representations) рисунка или в подписи.

## Артефакты [#artifacts]

Некоторые вещи на странице не имеют семантического значения и не относятся к содержимому документа. Мы называем такие элементы _артефактами._ Артефакты скрыты от ВТ и перепрофилирования и исчезают при переформатировании. Вот несколько примеров артефактов:

- Дефисы, вставляемые автоматическим переносом в конце строки
- Верхние и нижние колонтитулы на каждой странице
- Чисто декоративное фоновое изображение страницы

В целом, каждый элемент на странице должен либо иметь какой-то способ, которым ВТ может его объявить, либо быть артефактом, чтобы документ считался доступным.

Typst автоматически помечает многие элементы макета, такие как верхние и нижние колонтитулы, фон и передний план страницы, а также автоматический перенос, как артефакты. Однако если вы хотите добавить в документ чисто декоративное содержимое, вы можете использовать функцию [`pdf.artifact`](/docs/typst/reference/format/pdf/artifact), чтобы пометить фрагмент содержимого как артефакт. Если вы не уверены, следует ли помечать элемент как артефакт, задайте себе такой вопрос: было бы чисто раздражающим, если бы программа экранного доступа объявила вам этот элемент? Тогда это, возможно, артефакт. Если же, наоборот, было бы полезно, чтобы его объявили, то это не артефакт.

По техническим причинам, оказавшись внутри артефакта, содержимое не может снова стать семантическим. Чтобы наложить артефакты и семантическое содержимое, используйте [`place`](/docs/typst/reference/layout/place), чтобы переместить содержимое друг на друга.

Обратите внимание, что Typst будет помечать фигуры и пути, такие как [`square`](/docs/typst/reference/visualize/square) и [`circle`](/docs/typst/reference/visualize/circle), как артефакты, тогда как их содержимое останется семантически значимым и доступным для ВТ. Если ваши фигуры имеют семантическое значение, пожалуйста, оберните их в элемент [`figure`](/docs/typst/reference/model/figure), чтобы предоставить альтернативное текстовое описание.

## Использование цвета и контраст [#color-use-and-contrast]

Универсальный доступ означает не только то, что ваш документ работает с ВТ, переформатированием и перепрофилированием, но и то, что визуальный доступ возможен для всех, включая людей с нарушениями зрения. Не только старение часто сопровождается ухудшением зрения — значительная часть людей имеет проблемы с различением цвета: около 8% мужчин и 0,5% женщин страдают дальтонизмом.

Это означает, что цвет не должен быть единственным способом, которым вы делаете информацию доступной для зрячих пользователей в ваших документах. В качестве примера рассмотрим столбчатую диаграмму с накоплением с несколькими цветными сегментами на каждый столбец. Наш пример показывает диаграмму производства электроэнергии в Германии по видам<sup>[1](#loc-3)</sup>. На картинке вы видите диаграмму в её обычном виде и симуляцию того, как она выглядела бы для людей с дальтонизмом типа дейтеранопии. Вы можете видеть, что обе пары первого и последнего сегментов выглядят синими, а центральная пара выглядит желтоватой. Первая задача для пользователя с дальтонизмом — таким образом, разобрать границу столбца «Возобновляемые источники» и «Ископаемое топливо». Затем они должны отслеживать, какой столбец какой, только по их порядку, что увеличивает их умственную нагрузку. Способ сделать эту диаграмму ещё менее доступной — сделать порядок сегментов не совпадающим с их порядком в легенде.

Как мы можем улучшить диаграмму? Во-первых, убедитесь, что никакая информация не передаётся исключительно через использование цвета. Один из возможных способов сделать это — добавить узор к каждому столбцу. Затем мы можем помочь пользователю разобрать границы каждого сегмента, добавив высококонтрастную границу. Тогда наша диаграмма могла бы выглядеть примерно так:

<img src="/typst_docs_assets/images/xdt7S-4iE1sJyzrU1RNsnA.png" alt="" width="958" height="637" />

Это можно было бы дополнительно улучшить, выбрав цвета, различимые для людей, страдающих распространёнными типами дальтонизма. Вы также можете доработать дизайн, выбрав двухцветные узоры, выровняв их по столбцам или изменив использование шрифтов.

Вы можете проверить свой дизайн в веб-приложении с помощью встроенного симулятора дальтонизма. Чтобы использовать его, откройте меню «View» и выберите нужный режим в меню «Simulate color blindness». Вы также можете использовать другие инструменты в интернете, чтобы [симулировать цветовосприятие при различных видах дальтонизма](https://daltonlens.org/colorblindness-simulator), если вы не используете наше веб-приложение.

Также учитывайте цветовой контраст между фоном и передним планом. Например, если вы используете светло-серый текст для сносок, они могут стать трудночитаемыми. Другая ситуация, которая часто приводит к низкому контрасту, — это наложение текста на изображение.

<img src="/typst_docs_assets/images/-5cG3ELE6XV8cR7rJISaqQ.png" alt="" width="1536" height="708" />

В нашем примере мы видим два дизайна выносных блоков. Поскольку эти блоки призваны помочь пользователю избежать опасности, крайне важно, чтобы он действительно мог их прочитать. Однако в первом блоке фон довольно светлый, что затрудняет различение блока. Хуже того, красный текст трудно читать на светло-красном фоне. Текст имеет коэффициент контрастности 2,8:1, не достигая планки 4,5:1, установленной Руководствами по доступности веб-контента (WCAG). Аналогично, блок имеет коэффициент контрастности 1,4:1 с белым фоном страницы, не достигая порога 3:1 для графических объектов.

Цвета во втором примере были скорректированы, чтобы соответствовать порогам цветового контраста WCAG AA. Читать текст в блоке должно быть заметно легче, даже если у вас хорошее зрение!

Существуют [инструменты для сравнения того, насколько контрастна пара цветов](https://webaim.org/resources/contrastchecker/) в качестве переднего плана и фона. Наиболее распространённый — коэффициент цветового контраста WCAG. Для заданного размера шрифта пара цветов может либо не пройти тест, либо достичь уровня AA, либо достичь более высокого уровня AAA. Стремитесь как минимум к контрасту AA для всех ваших цветовых пар.

| **Содержимое** | **Коэффициент AA** | **Коэффициент AAA** |
| --- | --- | --- |
| Крупный текст (≥18pt, или полужирный и ≥14pt) | 3:1 | 4,5:1 |
| Мелкий текст | 4,5:1 | 7:1 |
| Нетекстовое содержимое | 3:1 | 3:1 |

Обратите внимание, что распространённые фреймворки доступности, такие как WCAG, делают исключение для чисто декоративного текста и логотипов: благодаря их графическому характеру они могут иметь коэффициенты контрастности, не достигающие коэффициента контраста AA.

## Текстовые представления [#textual-representations]

Чтобы поддерживать использование ВТ и некоторые рабочие процессы перепрофилирования, все элементы с семантическим значением должны иметь текстовое представление. Подумайте об этом в терминах универсального доступа: если элемент не является [артефактом](#artifacts), он имеет семантическое значение. Если же ВТ не может воспринять элемент, полное семантическое значение документа недоступно пользователям ВТ. Следовательно, чтобы обеспечить универсальный доступ, используйте механизмы, встроенные в Typst, для предоставления альтернативных представлений.

Когда вы добавляете изображение, обязательно используйте [`аргумент alt функции image`](/docs/typst/reference/visualize/image#parameters-alt), чтобы описать, что видно на изображении. Это альтернативное описание (иногда называемое альтернативным текстом) должно описывать суть изображения: подумайте, как бы вы описали изображение другу, если бы позвонили ему по телефону. Чтобы написать хорошие альтернативные описания, учитывайте контекст, в котором появляется изображение:

<TypstRender
  code={`
  #image("heron.jpg", alt: "?")

  Herons have feet with interdigital
  webbing, allowing for good mobility
  when swimming, and wings that span
  up to 2.3 m.
`}
  image="/typst_docs_assets/images/vdfPsGaVd3MjF_oVpWq-qA.png"
  alt=""
  editable={true}
/>

Каким могло бы быть хорошее альтернативное описание для [этого изображения](https://commons.wikimedia.org/wiki/File:Reiher_im_Flug.jpg)? Давайте рассмотрим несколько примеров того, чего _не_ следует делать:

- `"Image of a heron"`<br />❌ Программа экранного доступа уже сама объявит изображение, поэтому говорить, что это изображение, избыточно. В этом примере пользователь ВТ услышит «Image, Image of a heron».
- `"A bird"`<br />❌ Альтернативное описание недостаточно конкретно. Например, для пользователя важно, что на изображении изображена цапля и видны как её лапы, так и крылья.
- `"Gray heron in flight. Picture by Makasch1966 on Wikimedia Commons, CC Attribution 4.0 International license"`<br />❌ Альтернативное описание не должно включать детали, не видимые на изображении, такие как атрибуция, шутки или метаданные. Имейте в виду, что оно недоступно зрячим пользователям. Эта информация относится в другое место.
- `"Gray heron flying low, heading from the right to left. Its feet are extended and slightly point downwards, touching a blurred horizon where a dark forest becomes visible. The bird's wings are extended and arc upwards. There are out-of-focus branches visible in the lower left corner of the image."`<br />❌ Альтернативное описание слишком многословно. Проявите рассудительность и определите, насколько изображение важно для содержимого. Подумайте, как долго зрячий пользователь реалистично смотрел бы на изображение; ваш альтернативный текст должен требовать примерно таких же усилий для «восприятия». Например, анатомическое описание, приведённое выше, могло бы подойти для более длинного обсуждения в учебнике по зоологии, тогда как информация о композиции полезна при написании о фотографии. Контекст, в котором приводится пример изображения, относительно короткий, поэтому напишите более краткое описание.

Вместо этого в данном примере вы могли бы использовать такой альтернативный текст:

- `"Heron in flight with feet and wings spread"`<br />✅ Это альтернативное описание описывает изображение, соответствует контексту и его краткости.

В интернете есть ресурсы, [чтобы узнать больше о написании хороших альтернативных описаний](https://webaim.org/techniques/alttext/). Требование добавлять альтернативный текст к изображениям распространяется на все форматы изображений. В настоящее время Typst не сохраняет теги изображения PDF в скомпилированном документе, даже если сам файл изображения PDF был доступным.

Не используйте изображения текста; аналогично, не используйте операции с путями для ручного рисования текста. Typst не сможет обработать текст на любых изображениях, чтобы сделать его доступным так же, как собственный текст. Из этого правила есть одно исключение: используйте изображение текста, когда внешний вид текста существенен для семантического значения документа и не может быть воспроизведён средствами Typst. В этом случае вы должны описать как текстовое содержимое, так и существенные визуальные характеристики в альтернативном описании.

Как и функция image, функция figure имеет [`атрибут alt`](/docs/typst/reference/model/figure#parameters-alt). Когда вы используете этот атрибут, многие программы экранного доступа и другие ВТ не будут объявлять содержимое внутри figure, а вместо этого просто прочитают альтернативное описание. Ваше альтернативное описание должно быть достаточно полным, чтобы пользователю ВТ не нужно было обращаться к телу figure. Используйте альтернативное описание только в том случае, если содержимое figure иным образом недоступно. Например, не используйте атрибут `alt` у figure, если он содержит элемент `table`, но используйте его, если вы использовали внутри фигуры, которые несут семантическое значение. Если вы указываете и `alt`, и `caption`, ВТ прочитают оба. Когда ваш figure содержит изображение, задайте альтернативное описание [на самом изображении](/docs/typst/reference/visualize/image#parameters-alt), а не на figure. Не задавайте оба, так как описание изображения будет переопределено описанием figure.

```typst
#figure(
  alt: "Star with a blue outline",
  curve(
    stroke: blue,
    curve.move((25pt, 0pt)),
    curve.line((10pt, 50pt)),
    curve.line((50pt, 20pt)),
    curve.line((0pt, 20pt)),
    curve.line((40pt, 50pt)),
    curve.close(),
  ),
)
```

Наконец, вы можете задать альтернативное описание для математики с помощью [`math.equation`](/docs/typst/reference/math/equation). Описывайте свою формулу так, как если бы её читали вслух на естественном языке. В настоящее время добавление альтернативного описания требуется для доступной математики во всех форматах экспорта. Отсутствие альтернативного описания для вашей формулы приведёт к сбою экспорта PDF/UA-1. В будущем Typst будет автоматически делать математику доступной в HTML и PDF 2.0, используя технологию MathML.

```typst
#math.equation(
  alt: "a squared plus b squared equals c squared",
  block: true,
  $ a^2 + b^2 = c^2 $,
)
```

Ещё один элемент, который представляет себя как текст, — это ссылки. Лучше избегать неинформативных текстов ссылок, таких как _здесь_ или _перейти._ Такие тексты ссылок также вредят поисковой оптимизации (SEO), если это важно для вашего документа. Вместо этого постарайтесь, чтобы ссылка содержала текст о том, куда она указывает. Обратите внимание, что, если вы не стремитесь к высшему уровню доступности, также допустимо, если сама ссылка неинформативна, но её назначение можно понять из содержимого, непосредственно её окружающего.

## Естественный язык [#natural-language]

Чтобы программы экранного доступа правильно произносили ваш документ, а программное обеспечение для перевода работало должным образом, вы должны указать, на каком естественном языке написан ваш документ. Используйте правило [`#set text(lang: "..")`](/docs/typst/reference/text/text#parameters-lang) в самом начале вашего документа или возможность вашего шаблона задать язык. Если вы этого не сделаете, Typst будет считать, что ваше содержимое на английском языке. Выбранный вами естественный язык влияет не только на доступность, но и на то, как Typst будет применять перенос, какие типографские соглашения применяются, на подписи рисунков и ссылок, а в веб-приложении — на то, какой язык используется для проверки орфографии.

Если вы используете язык со значительными различиями между регионами, такой как китайский или английский, также используйте [`аргумент region`](/docs/typst/reference/text/text#parameters-region). Например, китайский в том виде, в каком на нём говорят в Гонконге, выглядел бы так:

```typst
#set text(lang: "zh", region: "HK")
```

Чтобы указать ваш язык, используйте коды ISO 639. Для регионов используйте код [ISO 3166-1 alpha-2](https://en.wikipedia.org/wiki/ISO_3166-1_alpha-2). ISO 639 содержит три варианта: один для двухбуквенных языковых кодов, таких как «de» для немецкого [(ISO 639-1)](https://en.wikipedia.org/wiki/List_of_ISO_639_language_codes), и два для трёхбуквенных языковых кодов, таких как «deu» ([ISO 639-2](https://en.wikipedia.org/wiki/List_of_ISO_639-2_codes) и [ISO 639-3](https://en.wikipedia.org/wiki/List_of_ISO_639-3_codes)). Если у вашего языка есть двухбуквенный код ISO 639-1, всегда предпочитайте использовать его. ISO 639-2 и 639-3 разделяют большинство кодов, но есть некоторые различия. Когда ваш языковой код различается между двумя стандартами, используйте ISO 639-2 при экспорте в PDF 1.7 (по умолчанию в Typst) и ниже, а ISO 639-3 — при экспорте в PDF 2.0 и HTML.

Существуют три специальных языковых кода, определённых как в ISO 639-2, так и в ISO 639-3, которые вы можете использовать, когда указать обычный языковой код сложно:

- `zxx` для текста, который не на естественном языке
- `und` для текста, естественный язык которого вы не можете определить
- `mis` для текста на языках, которым не был присвоен языковой код

Если ваш документ содержит текст на нескольких языках, вы можете использовать функцию text или ограниченное областью правило set для text, чтобы заключить вхождения других языков:

<TypstRender
  code={`
  This is #text(lang: "fr")[français].

  #[
    #set text(lang: "es")
    Este es un fragmento más largo
    del texto en español.
  ]
`}
  image="/typst_docs_assets/images/BeOpaECqlyd5U6JOpC2KlQ.png"
  alt=""
  editable={true}
/>

## Заголовок документа и заголовки [#document-title-and-headings]

Присвоение заголовка вашему документу облегчает его поиск и навигацию между ним и другими документами как для пользователей ВТ, так и для обычных пользователей программ просмотра PDF. Именно поэтому стандарты доступности, такие как WCAG и PDF/UA, требуют, чтобы вы задали машиночитаемый заголовок для вашего документа.

Чтобы сделать это в Typst, поместите это правило set в ваш документ перед любым содержимым:

```typst
#set document(title: [GlorboCorp Q1 2023 Revenue Report])
```

Это установит [заголовок в метаданных документа](/docs/typst/reference/model/document#parameters-title) и в строке заголовка программы просмотра PDF или веб-браузера. Если при использовании шаблона это приводит к ошибке, подумайте, не предоставляет ли ваш шаблон альтернативный способ установки заголовка документа.

Скорее всего, вы также захотите включить заголовок видимо в ваш документ. Для этого используйте элемент [`title`](/docs/typst/reference/model/title). Когда вы добавляете вызов элемента title без аргументов, он выведет содержимое того, что вы установили в качестве заголовка документа. В качестве альтернативы вы можете настроить заголовок, передав содержимое в качестве позиционного аргумента body. Не используйте элемент title более одного раза в вашем документе.

Никогда не используйте заголовок для заголовка вашего документа; вместо этого используйте элемент title. Если у вас есть опыт работы с HTML, важно помнить, что семантика элемента heading в Typst отличается от заголовков HTML. В документах Typst рекомендуется использовать несколько заголовков первого уровня для заголовков разделов. При экспорте в HTML [title](/docs/typst/reference/model/title) будет сериализован как тег `h1`, а [заголовок первого уровня](/docs/typst/reference/model/heading#parameters-level) будет сериализован как тег `h2`. При экспорте в PDF заголовок и заголовки разделов будут корректно помечены тегами в зависимости от целевой версии PDF.

Важно, чтобы последовательность используемых вами заголовков была последовательной: никогда не пропускайте уровень заголовка при углублении. Это означает, что за заголовком третьего уровня должен следовать заголовок четвёртого уровня или ниже, но никогда — заголовок пятого уровня или выше.

```typst
// ❌ Don't do this:
= First level heading
=== Third level heading
```

Обратите внимание, что для прохождения [автоматической проверки доступности в Adobe Acrobat](https://helpx.adobe.com/acrobat/using/create-verify-pdf-accessibility.html#Bookmarks) документы объёмом 21 страница и более должны содержать заголовки в структуре закладок.

## Стандарты доступности и законодательство [#accessibility-standards-and-legislation]

Typst может помочь вам подтвердить, что ваш документ доступен, проверив его на соответствие международным стандартам. Для экспорта в PDF существует несколько стандартов доступных файлов, наиболее заметным из которых является стандарт PDF/UA. Его первая часть (PDF/UA-1) уже поддерживается Typst, а поддержка второй части (PDF/UA-2) запланирована на будущее. Ниже вы найдёте объяснение всех соответствующих стандартов:

- **Tagged PDF:** PDF с тегами содержат машиночитаемые данные о семантической структуре документа, которые ВТ может разобрать. Typst будет записывать PDF с тегами по умолчанию, но имейте в виду, что Typst может записывать подходящие теги только в том случае, если он знает о семантической структуре вашего документа. Обратитесь к разделу [_Сохранение семантики_](#maintaining-semantics), чтобы узнать, как использовать элементы Typst для передачи семантики. Чтобы обеспечить универсальный доступ, вы также несёте ответственность за предоставление текстового представления нетекстового содержимого самостоятельно.
- **PDF/UA-1:** Стандарт PDF/UA объясняет, как написать файл PDF 1.7, оптимизированный для универсального доступа. Он подразумевает PDF с тегами, требует альтернативных описаний для изображений и математики, требует заголовок документа и вводит правила о том, как должно быть структурировано содержимое документа, например таблицы. Если вы следуете этому руководству, вы уже избегаете большинства ошибок компилятора, которые могут возникнуть при экспорте PDF/UA-1.
- **PDF/UA-2:** Существует также более поздняя часть PDF/UA-2, ориентированная на файлы PDF 2.0. Она улучшает доступность математики и некоторых семантических элементов. Поддержка PDF/UA-2 пока недоступна в Typst, но запланирована.
- **Well Tagged PDF (WTPDF):** Это отраслевой стандарт, очень похожий на PDF/UA-2. Как и PDF/UA-2, он в настоящее время не поддерживается Typst. Изначально он был разработан потому, что обе части спецификации PDF/UA были доступны только за высокую плату от Международной организации по стандартизации. Поэтому [WTPDF](https://pdfa.org/wtpdf/) был разработан так, чтобы все соответствующие файлы могли также заявлять о соответствии PDF/UA-2. К настоящему времени [обе части спецификации PDF/UA доступны бесплатно](https://pdfa.org/sponsored-standards/), что снижает актуальность WTPDF.
- **PDF/A-1a:** Стандарт PDF/A описывает, как создавать PDF-файлы, хорошо подходящие для архивирования. Части с первой по третью стандарта PDF/A имеют несколько уровней соответствия. Самый строгий уровень соответствия A содержит правила доступности, поскольку только файлы, отвечающие этим правилам, остаются пригодными для использования максимально широким кругом людей в далёком будущем. Уровень A подразумевает соответствие Tagged PDF и обязывает вас предоставлять альтернативные описания для изображений. Также применяются другие правила PDF/A, не связанные с доступностью, например о прозрачности, цветах и другое. Эта часть стандарта PDF/A основана на устаревшей спецификации PDF 1.4. Используйте её только в том случае, если этого требует ваша площадка или если вам нужен очень совместимый файл. В противном случае PDF/UA-1 и вторая и третья части PDF/A предоставляют лучшие альтернативы.
- **PDF/A-2a** и **PDF/A-3a:** Как и первая часть PDF/A, эти стандарты сосредоточены на создании файлов, подходящих для архивирования и долгосрочного хранения. Оба этих стандарта ориентированы на более новую версию PDF 1.7 вместо PDF 1.4. Здесь также самый строгий уровень соответствия A содержит правила доступности. В дополнение к правилам PDF/A-1a эти стандарты запрещают использование символов из [области частного использования Unicode](https://en.wikipedia.org/wiki/Private_Use_Areas), значение которых не определено универсально. Улучшения по сравнению с PDF/A-1 включают возможность использования прозрачности и лучшее переформатирование. При выборе между этими двумя частями стандарта PDF/A выбирайте PDF/A-2a, если вам не нужно [прикреплять](/docs/typst/reference/format/pdf/attach) другие файлы. Обратите внимание, что уровень соответствия A был удалён из PDF/A-4 в пользу выделенного стандарта PDF/UA.

[Справочная страница PDF](/docs/typst/reference/format/pdf#parameters-standard) содержит больше информации о каждом поддерживаемом стандарте. Чтобы включить PDF/UA, PDF/A-2a или PDF/A-3a, используйте [соответствующий флаг в CLI](/docs/typst/reference/format/pdf#command-line) или используйте выпадающий список экспорта и нажмите на PDF в веб-приложении. Вы можете комбинировать совместимые стандарты PDF/A и PDF/UA. Для документов, ориентированных на доступность, мы рекомендуем комбинировать PDF/UA-1 с PDF/A-2a или PDF/A-3a.

Когда вы выбираете один из этих стандартов для экспорта в PDF, Typst обнаружит, нарушаете ли вы их правила, и прервёт экспорт с описательным сообщением об ошибке. Для самой строгой проверки доступности, доступной в настоящее время, выберите PDF/UA-1. Не отключайте тегирование, если у вас нет веской причины, так как теги обеспечивают базовый уровень доступности для всех экспортируемых вами документов.

Возможно, вы уже заметили, что некоторые факторы, влияющие на универсальный доступ, трудно проверить автоматически. Например, в настоящее время Typst не будет автоматически проверять, достаточны ли ваши цветовые контрасты или соответствует ли настроенный естественный язык фактическому естественному языку (хотя количество ошибок проверки орфографии должно дать подсказку, если вы используете веб-приложение). Существуют два международных стандарта, которые более подробно рассматривают некоторые из этих человеческих факторов:

- **[Руководства по доступности веб-контента (WCAG)](https://www.w3.org/TR/WCAG21/)**: Разработанные W3C, крупным международным консорциумом, стоящим за технологиями, которые обеспечивают работу интернета, WCAG описывают, как сделать веб-сайт доступным. Все эти правила применимы к выводу HTML в Typst, и многие из них применимы к его выводу PDF. WCAG разделяет свои правила на три уровня: A, AA и AAA. Рекомендуется, чтобы обычные документы стремились к AA. Если у вас высокие стандарты универсального доступа, вы также можете рассмотреть критерии успеха AAA. Однако Typst пока не предоставляет все функции PDF, необходимые для соответствия AAA, например доступный для ВТ способ определения расшифровок для аббревиатур.
- **[Европейская норма EN 301 549](https://www.etsi.org/deliver/etsi_en/301500_301599/301549/03.02.01_60/en_301549v030201p.pdf)**: Её раздел 9 описывает, как создавать доступные веб-сайты, а раздел 10 описывает, какие правила применяются к невеб-документам, включая PDF-файлы, созданные Typst. В нём указывается, какие пункты WCAG также применимы к PDF. Соответствие этому стандарту — хорошее начало для соблюдения законодательства ЕС и национальных законов о доступности.

Имейте в виду, что для соответствия EN 301 549 и соответствующим положениям WCAG ваш документ должен быть помечен тегами. Если вы стремитесь к соответствию, мы настоятельно рекомендуем использовать PDF/UA-1 для экспорта, чтобы автоматизировать многие проверки критериев успеха внутри.

Во многих странах действует законодательство о доступности, которое требует от вас создавать доступные файлы при определённых обстоятельствах. Вот лишь некоторые из них:

- **[Европейский акт о доступности (EAA, EU 2019/882)](https://eur-lex.europa.eu/eli/dir/2019/882/oj)**: Этот регламент применяется к электронным книгам, потребительским банковским услугам, услугам электронной коммерции и многому другому. Он требует, чтобы файлы, распространяемые в этих приложениях, были доступными.
- **Закон об американцах с инвалидностью (ADA)**: Министерство юстиции [потребует от организаций государственного сектора предоставлять файлы](https://www.ada.gov/law-and-regs/regulations/title-ii-2010-regulations/) в соответствии с WCAG в рамках Раздела II ADA к 2026 году. Аналогично, [частные организации могут нести ответственность](https://www.boia.org/blog/the-robles-v.-dominos-settlement-and-why-it-matters) за недоступные цифровые услуги в соответствии с ADA и законодательством штатов.

Использование этого руководства может помочь вам достичь соответствия любому из этих регламентов.

## Тестирование на доступность [#testing-for-accessibility]

Чтобы проверить, доступен ли ваш PDF-документ, вы можете использовать автоматические инструменты и ручное тестирование. Некоторые стандарты, такие как PDF/UA и PDF/A, можно проверить исключительно с помощью автоматических инструментов, тогда как некоторые правила в WCAG и других стандартах требуют ручных проверок. Многие из автоматизируемых проверок автоматически проходят в Typst, когда включён Tagged PDF. Для многих других автоматизируемых проверок вы можете включить экспорт PDF/UA-1, чтобы Typst выполнял их вместо вас. Автоматические инструменты могут обеспечить лишь базовый уровень доступности. Для истинно универсального доступа лучше всего, если вы сами попробуете документ с ВТ.

Вот список автоматических проверщиков, которые стоит попробовать для проверки соответствия:

- **[veraPDF](https://verapdf.org):** Этот инструмент с открытым исходным кодом может проверить, соответствует ли ваш PDF-файл тем частям стандартов PDF/A и PDF/UA, о соответствии которым он заявил. Используйте этот инструмент, если вы выбрали один из этих стандартов при экспорте. Сбои считаются ошибками в Typst, и о них следует [сообщать на GitHub](https://github.com/typst/typst/issues).
- **[PDF Accessibility Checker (PAC)](https://pac.pdf-accessibility.org/en):** Бесплатная программа PAC проверяет, соответствует ли ваш документ правилам PDF/UA и WCAG. Когда вы получаете серьёзную ошибку на вкладке PDF/UA, это считается ошибкой в Typst, и о ней следует [сообщать на GitHub](https://github.com/typst/typst/issues). Предупреждения на вкладках PDF/UA и Quality могут быть ошибками, проблемами в вашем документе или ни тем, ни другим. Проверьте на [Форуме](https://forum.typst.app/) или в [Discord](https://discord.gg/2uDybryKPe), если вы не уверены. Ошибки и предупреждения на вкладке WCAG указывают на проблемы в вашем документе.
- **[Проверка доступности в Adobe Acrobat Pro](https://helpx.adobe.com/acrobat/using/create-verify-pdf-accessibility.html):** Проверщик доступности в платной версии Adobe Acrobat проверяет все PDF-документы на наличие проблем. Вместо проверки соответствия известному международному или отраслевому стандарту Adobe создала свой собственный набор тестов. Поскольку правила, лежащие в основе этих тестов, иногда противоречат международным стандартам, таким как PDF/UA, некоторые проверки Acrobat, как ожидается, будут завершаться неудачей для документов Typst<sup>[2](#loc-4)</sup>. Другие проверки, такие как проверка контраста, полезны и указывают на проблемы в вашем документе.

При выполнении ручной проверки вы можете начать с контрольного списка. Если ваша организация уделяет внимание доступности, у неё иногда будет свой собственный список. При его отсутствии вы можете попробовать списки от университетов, таких как [Universität Bremen (на английском)](https://www.uni-bremen.de/fileadmin/user_upload/universitaet/Digitale_Transformation/Projekt_BALLON/Checklisten/2._Auflage_englisch/Checklist_for_accessible_PDF_ENG-US_ver2.pdf), или правительств, например [Канады](https://a11y.canada.ca/en/pdf-accessibility-checklist/), или от [Управления социального обеспечения США](https://www.ssa.gov/accessibility/checklists/PDF_508_Compliance_Checklist.pdf). Хотя эти контрольные списки различаются по многословности, все они охватывают наиболее существенные ручные проверки. Многие из технических проверок в них можно пропустить, если вы выберете экспорт PDF/UA-1 в Typst. Если вы не уверены, какой контрольный список использовать, выберите тот, что от организации, культурно близкой к вашей.

Однако для достижения высшего стандарта доступности для широко распространённых документов рассмотрите проверку вашего документа с помощью ВТ. Хотя существует множество продуктов ВТ и программ просмотра PDF, обычно достаточно протестировать одну комбинацию. Какая лучше, зависит от вашей операционной системы:

- Windows: Тестируйте с [Adobe Acrobat](https://www.adobe.com/acrobat.html) и [NVDA](https://www.nvaccess.org/download/). NVDA — бесплатное программное обеспечение с открытым исходным кодом. Доступна бесплатная версия Acrobat.
- macOS: Тестируйте с [Adobe Acrobat](https://www.adobe.com/acrobat.html) и [VoiceOver](https://support.apple.com/guide/voiceover/welcome/mac). VoiceOver — это программа экранного доступа, встроенная в macOS и другие платформы Apple.
- Linux: Тестируйте с [Evince](https://wiki.gnome.org/Apps/Evince/) или [Okular](https://okular.kde.org/) и [Orca](https://orca.gnome.org). Все три инструмента — бесплатное программное обеспечение с открытым исходным кодом. Однако поддержка ВТ на платформах Linux отстаёт от того, что доступно на Windows и macOS. Аналогично, Evince и Okular имеют меньшую поддержку доступности, чем Acrobat. Мы настоятельно рекомендуем вместо этого тестировать с Acrobat.

При первом знакомстве с тестированием рассмотрите возможность прохождения интерактивной обучающей программы, которую предлагает ваша программа экранного доступа, если таковая имеется. Уверенное владение программой экранного доступа помогает вам воспринимать ваш документ так, как это делает пользователь, работающий с ней постоянно. При проверке вашего документа убедитесь, что он не только делает доступной ту же информацию, что доступна зрячему пользователю, но и что по нему легко перемещаться. Опыт ваших пользователей будет различаться в зависимости от пары программы просмотра PDF и ВТ, которые они используют.

## Ограничения и соображения для форматов экспорта [#limits-and-considerations-for-export-formats]

Даже когда вы проектируете документ с учётом доступности, вы должны осознавать ограничения вашего формата экспорта. По сути, поддержку ВТ для PDF-файлов сложнее реализовать, чем для других форматов, таких как HTML. PDF был задуман в 1993 году для точного отображения печатных документов на компьютере. Функции доступности были впервые добавлены в PDF 1.4 в 2001 году и улучшены в PDF 1.5 (2003) и PDF 2.0 (2017). Напротив, HTML предлагает более богатую семантическую модель и большую гибкость, поэтому поддержка ВТ в браузерах обычно превосходит то, что возможно в программах просмотра PDF.

Также помните, что PDF-файлы в основном статичны. Это позволяет вам игнорировать многие правила WCAG и EN 301 549, предназначенные для интерактивного содержимого и мультимедиа. Однако отсутствие интерактивности также затрудняет пользователям настройку макета документа под свои нужды.

Например, [Критерий успеха WCAG 1.4.12](https://www.w3.org/WAI/WCAG21/Understanding/text-spacing.html) (закреплённый в пункте 10.1.4.12 EN 301 549) предписывает, что пользователь должен иметь возможность увеличивать межсимвольный, межбуквенный, межстрочный интервалы и интервал между абзацами до очень больших значений. Это приносит пользу пользователям с ослабленным зрением или дислексией. Критерий успеха не требует, чтобы вы проектировали документ с этими параметрами макета. Вместо этого он требует лишь механизма, с помощью которого пользователи могут увеличивать эти параметры при чтении документа. Для HTML-файлов легко соблюсти этот критерий успеха, поскольку браузер позволяет пользователю переопределять эти параметры интервалов на странице. Для PDF ситуация более тонкая: теоретически Typst добавляет в файл теги и атрибуты, предназначенные для переформатирования. Программа чтения PDF при переформатировании могла бы позволить своему пользователю увеличивать интервалы сверх того, что закреплено в этих тегах. На практике нам неизвестна программа просмотра PDF с такой функцией. Вместо этого этот критерий успеха можно выполнить, перепрофилировав PDF в HTML-файл и открыв его в браузере.

На практике, даже если ваш файл технически соответствует требованиям, вы не можете ожидать, что ваши пользователи знают об этих обходных путях. Поэтому, если вы стремитесь соответствовать высшим стандартам универсального доступа, рассмотрите возможность распространения HTML-версии вашего документа вместе с PDF. Экспортируйте этот файл напрямую с помощью [экспорта в HTML](/docs/typst/reference/format/html) в Typst (в режиме предварительного просмотра). Хотя экспорт в HTML не сохранит многие аспекты вашего визуального макета, он создаст файл, который использует семантический HTML и технологии, такие как [Digital Publishing ARIA](https://www.w3.org/TR/dpub-aria-1.1/), для обеспечения универсального доступа. Он будет более высокого качества, чем PDF-файл, перепрофилированный в HTML.

Наконец, помните, что PDF-файлы предназначены для печати. Следовательно, вы не должны предполагать, что интерактивные функции, такие как ссылки, доступны пользователям, которые решили распечатать ваш документ.

Как упоминалось выше, файлы, созданные при экспорте в PNG и SVG, не являются доступными.
